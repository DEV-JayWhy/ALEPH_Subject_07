# 플랜두씨 다이어리 1 · ALEPH 과제 6

Plan → Do → See 공개 웹앱. 서버의 **이미 생성된** Supabase PostgreSQL 여섯 표를 사용한다. 이 소스에는 DB 생성/변경 SQL이나 자동 샘플 데이터 입력이 없다. 로그인 없이 누구나 읽고 편집할 수 있으므로 공개 가능한 내용만 기록한다.

## 1. 바로 시작하기

1. `config.js`에서 `supabaseUrl`에 Supabase 프로젝트 URL, `supabasePublishableKey`에 **공개용 publishable key**(또는 기존 anon key)를 넣는다. `sb_secret_...`, legacy service-role key, DB 비밀번호는 절대로 넣지 않는다.
2. 이 폴더에서 `python -m http.server 4173`을 실행하고 `http://localhost:4173`을 연다. Python 명령이 `python3`인 환경에서는 `python3 -m http.server 4173`. Node 설치나 `npm install`은 필요 없다.
3. Plan에서 실제 계획 양식 채우기 → 내용 확인 후 DB 저장. Do에서 정해둔 다섯 할 일의 **미정 값**(마감일·우선순위·태그·예상 분)을 정해 저장하고, 실제 시작/종료를 확인한 실행 기록만 입력한다. See에서 숫자를 눌러 원본을 검증한다.

`config.js`는 공개 설정 파일이므로 이후 GitHub 웹 업로드와 Vercel 배포에도 이 두 **공개 값만** 넣을 수 있다. 공개 키는 비밀번호가 아니다. 반면 현재 RLS 정책은 익명 편집을 허용하므로 다른 방문자도 공개 자료를 바꿀 수 있다. 이 과제의 로그인 없음 조건을 따른 것이다. DB 초기 SQL은 이미 적용되었으므로 재실행하지 않는다.

## 2. 심사자 확인 동선 · 세 단계

1. **Plan**: 실제 계획의 기간·우선순위·성공 기준·예상 분과 수정 이력 보기.
2. **Do**: 다섯 할 일을 검색·필터·정렬하고 각 할 일의 완료·취소와 실행 기록 보기.
3. **See**: 집계 카드를 눌러 할 일 ID, 완료 ID, 실행 ID와 시간 근거 보기. 개선점을 저장한 뒤 새 계획에 연결해 다음 Plan 상단에서 전달 문구 확인.

상단 **전체 자료 내보내기**는 여섯 표를 모두 읽어 JSON 한 파일을 다운로드한다. 삭제 처리된 할 일과 과거 완료·계획 버전도 포함한다. 새로고침 버튼과 브라우저 새로고침은 서버에서 다시 읽는다.

## 4. 저장 규칙과 구현 선택

- 날짜는 `YYYY-MM-DD` 그대로, 사건 시각은 서울 입력 `+09:00`을 UTC ISO로 변환해 `timestamptz`에 전송한다. 화면은 `Asia/Seoul`로 표시한다. 시간 합계는 전부 **분**.
- 카드 4 기본 모집단은 해당 계획의 `deleted_at IS NULL` 할 일 **전체**다. `reviews.period_start / period_end`는 돌아보기의 설명용 기간이며 기본 집계를 거르지 않는다.
- 검색·필터·정렬은 서버에서 불러온 현재 계획의 전체 할 일에 브라우저에서 적용한다. 현재 정렬 기준과 동률 ID 기준을 표시한다. 자료가 1000행을 넘으면 REST 조회를 페이지 단위로 반복한다.
- 완료가 실패하거나 결과가 불분명하면 `sessionStorage`에 **요청 UUID만** 남기고 같은 버튼의 재시도에 재사용한다. 본문 기록은 브라우저 저장소에 저장하지 않는다. 성공 후 키를 지운다. 완료 취소는 별도 RPC다.
- 다섯 할 일의 제목만 양식에 지정해 두었다. 마감일·태그·시간은 사용자가 결정한다. 최초 36분은 정확한 시작·종료 시각이 없으므로 실행 기록으로 생성하지 않는다.
- 개선점 연결은 `reviews.next_plan_id` 업데이트다. 다음 계획은 실제로 만든 뒤 선택한다. 동일한 다음 계획에 여러 돌아보기를 연결할 수 없다는 DB UNIQUE를 그대로 따른다.
- 별도 기간별 분석, 계정, 자동 시계, 알림, 가짜 데모 데이터는 추가하지 않았다.

## 6. 실제 환경 검증 목록

- 공개 키로 여섯 표 SELECT, 계획/할 일/실행/돌아보기 INSERT·UPDATE, 세 RPC가 되는지 확인. 401/403/404가 나면 프로젝트 URL·키, Data API 노출, GRANT/RLS와 함수 시그니처를 확인한다.
- 계획 수정 직후 `plan_revisions`의 v1/v2, 새로고침 후 ID·날짜·분 복원을 확인한다.
- 완료 요청 동일 UUID 두 번(네트워크 재시도 포함) → 활성 완료 1건·완료 수 +1, 완료 취소 → 0, 새 UUID 완료 → 1을 확인한다. UI의 빠른 연속 클릭은 요청 중 비활성 처리와 DB 제약이 함께 작동한다.
- 오늘/어제의 서울 날짜 경계, 마감일이 계획 기간 밖인 할 일 포함, 삭제된 할 일 제외, 한 할 일의 여러 막힌 기록을 한 번만 세는지 확인한다.
- 숫자별 상세 근거의 ID·합계가 `review_summary` 결과와 일치하는지 확인한다. 전체 Export를 열어 여섯 표와 삭제 기록을 확인한다.
- `<script>alert(1)</script>` 같은 공개 테스트 문구가 실행되지 않고 글자로만 표시되는지 확인한다.
- 비밀키가 `config.js`, Git 기록, 브라우저 네트워크·콘솔, 배포 파일에 없는지 확인한다. 공개 URL 두 개를 새 시크릿 창에서 열어 본다.

### 찰슨의 최종 검수 포인트

특히 `review_summary(plan_id)`의 기간 미필터, See 근거 집계의 동일한 모집단, `sessionStorage` 재시도 키 흐름, 공개 익명 편집 정책, SQL과 `contracts/pds-schema-v2.json` 일치 여부를 원문과 대조해 주세요. 실제 Supabase와 연결된 검증은 이 소스 제작 단계에서 수행하지 않았다.

## 7. 제출문 초안 · 실제 배포/검증 후 채우기

짧은 확인 방법 4줄:

1. 어디로 가나요 — `[배포 완료 후 결과물 URL]`
2. 세 단계 안에 무엇을 하나요 — `Plan에서 계획과 이력 → Do에서 할 일·실행 기록 → See에서 집계 숫자의 근거 확인`
3. 무엇이 보이면 통과인가요 — `실제 계획 1건, 할 일 5건, 실행 3건과 원본 ID가 연결된 집계, 새로고침 후 같은 값`
4. 안 될 때는 무엇이 보이나요 — `설정 누락 안내 또는 서버 연결 오류 메시지; 데이터 변경 실패는 오류 배너`

AI와 내 판단 3줄(사용자 검토 후 확정):

1. AI에게 맡긴 일 — `DB 계약에 맞는 Plan → Do → See UI 및 연결 코드 작성`
2. 내가 직접 판단한 일 — `실제 계획·할 일 마감일·태그·예상 분·실제 실행 시각·개선점 입력과 검증`
3. AI 제안을 따르지 않은 일 — `[실제 결정에 맞춰 작성. 없다면 이유를 설명]`
